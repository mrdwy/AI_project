# 第 3 章 · 用 AI 写嵌入式代码

> 对应总大纲 `docs/compose/spec/ai-embedded-teaching.md` 第 3 章。本章 5 讲，平台 **ESP32**（本章开头切平台）。
> 贯穿目标：学员能用「上下文工程 + 提示词模板 + 验证闭环」让 AI 写出可验证的嵌入式代码，而不是被 AI 编造的寄存器地址带进沟里。
> 本章承接第 2 章的手册阅读能力——AI 说的话，必须能对照手册/官方 API 指出出处。

---

## 3.1 换平台不换概念：从 STM32 到 ESP32

- **时长**：18 分钟
- **画面形式**：录屏 + 对照表（板书/图表）
- **本讲目标**：搭好 ESP32 开发环境（VSCode + ESP-IDF + Copilot）；能说出 STM32 ↔ ESP32 的概念对应；不害怕换平台。

### 前置

第 1–2 章完成；ESP32 开发板（DevKitC 或同类）已到手；已装 VSCode 与 Copilot。

### 知识点

**1. 为什么切到 ESP32**

| 维度 | STM32（第 1–2 章） | ESP32（第 3–6 章） |
|------|---------------------|----------------------|
| 学什么 | 经典寄存器原理、Keil 工程 | AI 协作、工程化、无线应用 |
| 工具链 | Keil MDK（不开源、学习曲线） | ESP-IDF（开源、命令行+插件、Git 友好） |
| AI 熟悉度 | 一般 | 高（Copilot 对 ESP-IDF / Arduino 熟） |
| 无线 | 无 | WiFi / BLE 原生 |
| 资料 | RM 详尽（学原理好） | 官方示例多（学工程好） |

- 关键话术：「平台是舞台，概念是剧本。舞台换了，剧本还在。」

**2. 概念对照表（本讲核心）**

| 概念 | STM32F103 | ESP32 |
|------|-----------|-------|
| 时钟使能 | `RCC->APBxENR` | 多数外设由驱动自动使能；`periph_module_enable()` |
| GPIO 配置 | CRL/CRH + ODR/BSRR | `gpio_config()` + `gpio_set_level()` |
| 外部中断 | EXTI + NVIC | `gpio_install_isr_service()` + `gpio_isr_handler_add()` |
| PWM | TIM + PSC/ARR/CCR | LEDC（`ledc_timer_config` / `ledc_channel_config`） |
| 串口 | USART + DR/SR | UART 驱动（`uart_driver_install` 等） |
| 延时 | `delay_ms` 或 SysTick | `vTaskDelay` / `esp_rom_delay_us` |
| 中断服务函数 | 自定义 `EXTIx_IRQHandler` | 注册的回调 `void IRAM_ATTR handler(void*)` |
| 内存映射 | RM0008 | TRM + 驱动 API（更常用 API 不直接摸寄存器） |

**3. 工具链搭建（ESP-IDF）**

1. 安装 VSCode 扩展：ESP-IDF（乐鑫官方）。
2. 安装 ESP-IDF（扩展里选版本，建议稳定版，如 v5.x）。
3. 选择目标芯片：ESP32 / ESP32-S3 / ESP32-C3（本课用经典 ESP32）。
4. 新建工程（hello_world 或 blink），`idf.py build` / `idf.py flash` / `idf.py monitor`。
5. 串口监视器：`idf.py monitor` 自带，波特率 115200。

**4. 与 Keil 的最大差异**

- **构建系统**：CMake + `idf.py`（命令行）取代 uVision 图形配置。工程里有 `CMakeLists.txt`、`sdkconfig`（配置项，类似裁剪菜单）。
- **配置**：`idf.py menuconfig` 菜单化配置，改完存到 `sdkconfig`。
- **调试**：可用 VSCode + ESP-IDF 调试（OpenOCD + JTAG），也可用 `idf.py monitor` 看日志。本课以「日志观测」为主，调试器为辅。
- 关键话术：「Keil 是图形化车间，idf.py 是命令行车间。指令记不住没关系，AI 会帮你补——但你要知道自己在干什么。」

### 演示步骤

1. **录屏（5 分钟）**：装 ESP-IDF 扩展、装工具链、选芯片；展示 `idf.py --version`。
2. **录屏（4 分钟）**：新建 blink 工程，`idf.py build` / `flash` / `monitor`，板上灯闪、串口有输出。
3. **录屏（5 分钟）**：打开 `sdkconfig` 与 `CMakeLists.txt`，简单讲各自作用；用 `menuconfig` 改一个串口波特率试试。
4. **录屏（3 分钟）**：对照表逐行过一遍——指着 STM32 的代码说「这就是 ESP32 的 XXX」。
5. **录屏（1 分钟）**：让 Copilot 解释一句 `gpio_config` 的参数，说明 API 级开发与寄存器级开发的差别。

### 口播要点

- 「别怕换平台。GPIO、中断、PWM、串口，四个概念一个没变，变的只是 API 名字。」
- 「ESP-IDF 是命令行驱动的，`idf.py build/flash/monitor` 三个指令先记牢。」
- 「`sdkconfig` 是这个工程的开关面板，改配置用 `menuconfig`，不要手改乱了。」
- 「第 2 章学的手册阅读能力，在这里变成『查 API 文档』的能力——同一个本事。」

### 踩坑提醒

- USB 线是充电线（无数据）——`idf.py flash` 找不到串口。
- 串口驱动（CP2102/CH340）没装。
- `idf.py` 不在 PATH——用 VSCode 扩展里的终端或 IDF PowerShell。
- 芯片型号选错（ESP32 vs S3 vs C3）——build 能过但 flash 失败或跑不起来。

### 课后动作

1. 把 blink 跑起来，并保存一份 `idf.py monitor` 的启动日志。
2. 填一份自己的《STM32 ↔ ESP32 概念对照表》，至少补一行：你想做的功能（如电机 PWM）在 ESP32 上叫什么。
3. 熟记三条命令：`idf.py build`、`idf.py flash`、`idf.py monitor`。

## 3.2 AI 协作的正确姿势

- **时长**：18 分钟
- **画面形式**：录屏 + 案例演示
- **本讲目标**：认清 AI 能做什么/不能做什么；建立「AI 说的寄存器/地址/位定义必须可查证」的红线；学会把 AI 当「高级实习生」而不是「权威」。

### 前置

3.1 完成，blink 工程能跑。

### 知识点

**1. AI 能做什么、不能做什么**

| 能做（放心用） | 不能做（必须人验证） |
|----------------|----------------------|
| 生成样板代码、初始化结构 | 保证寄存器地址/位定义正确（**可能编造**） |
| 解释代码、解释报错 | 保证时序、电气特性正确 |
| 按你给的文档写 API 调用 | 保证在你的具体硬件上「一定跑通」 |
| 重构、写注释、写测试 | 保证没有隐含的硬件陷阱 |
| 生成 commit message、文档 | 替代你做「示波器/逻辑分析仪」观测 |

- 关键话术：「AI 是高级实习生，不是权威。实习生写的代码，你要 review；实习生查的资料，你要核对。」

**2. 最大的坑：寄存器地址 / 位定义幻觉**

- 现象：AI 写出 `#define GPIOA_ODR *(volatile uint32_t*)0x40010C14` 之类——**地址可能是编的**。
- 为什么会这样：训练数据里有相似但不同的芯片；它在「补全模式」下倾向于给出看起来合理的数字。
- 验证方法（本课铁律）：
  1. **指出出处**：要求 AI 说出「这个地址来自哪份手册哪一页」。说不出来 = 不许用。
  2. **对照文档**：你自己打开 RM / API 文档，核对每一位。
  3. **运行验证**：跑起来看行为（但注意：能跑 ≠ 正确，可能只是巧合）。

**3. 三层模型在写代码场景的落地**

| 层 | 在写代码场景 | 例子 |
|----|--------------|------|
| 知道（30%） | 让 AI 解释概念、生成样板 | 「LEDC 怎么配 20kHz？」 |
| 验证（50%） | 你跑、你观测、你对照手册 | 烧录看现象、逻辑分析仪量频率 |
| 攻克（20%） | 你解决 AI 解决不了的 | 时序毛刺、电磁干扰、硬件故障 |

**4. AI 协作的「信任等级」**

| 等级 | 适用 | 动作 |
|------|------|------|
| 采信 | 样板代码、注释、文档、测试框架 | 采纳后 review |
| 核实 | API 调用、配置结构体 | 对照官方文档 |
| 存疑 | 寄存器地址、位定义、时序参数、芯片差异 | **必须**查手册/实测，说不清出处就不用 |

- 关键话术：「寄存器地址、位定义、时序数字——这三样是存疑区，不查手册不许写进代码。」

**5. 反面案例集（本讲要现场演示至少两个）**

| 案例 | 现象 | 正确做法 |
|------|------|----------|
| 编造寄存器地址 | AI 写 `0x4001_0C14`，查 RM 是别的地址 | 查 RM，改正确；或改用官方 API |
| 忘开时钟/外设 | 代码配置了但没输出 | 对照第 2 章三步开机；ESP-IDF 看驱动是否 install |
| 中断号/引脚错 | ISR 不触发 | 查 TRM 的引脚复用表 / GPIO matrix |
| 阻塞式死循环 | 主循环卡死、看门狗复位 | 改用状态机 / 任务延时；让 AI 解释阻塞点 |
| API 版本不匹配 | 编译不过 | 让 AI 明确 ESP-IDF 版本；对照 release notes |

### 演示步骤

1. **录屏（5 分钟）**：让 Copilot 写一个「纯寄存器点灯」——大概率给出编造或过时地址。当场打开 TRM/RM 对照，指出问题。
2. **录屏（4 分钟）**：要求 AI「说出每个寄存器地址的出处」，演示它给不出或含糊其辞。
3. **录屏（4 分钟）**：改用「基于官方 API + 给定文档」的提示词，让它写 LEDC PWM，行为正确。
4. **录屏（3 分钟）**：演示信任等级表——同一个问题，分别用「采信/核实/存疑」三种动作处理。
5. **录屏（2 分钟）**：小结三层模型在写代码场景的应用。

### 口播要点

- 「AI 写代码最大的风险不是『写不出来』，是『写出来了但地址是编的』。」
- 「问它『出处是哪一页』，比问它『你确定吗』有效得多。」
- 「寄存器地址、位定义、时序数字——存疑区，不查手册不许用。」
- 「能跑 ≠ 正确。硬件的坑，只有观测能证明。」

### 踩坑提醒

- 学员会说「AI 写的我跑起来亮了」就当正确——可能是巧合（比如地址刚好对）。强调可查证性。
- 学员会过度信任 AI 的解释（thinking 文本）——解释要对照手册。
- 不同芯片的「同名寄存器」地址不同——F103 与 ESP32 不可混用。

### 课后动作

1. 故意让 AI 写一段「STM32F103 纯寄存器串口」，逐行核对 3 个地址/位，写一篇《幻觉核查记录》。
2. 写下你的「信任等级」个人清单：哪些东西你打算采信、哪些必须核实、哪些存疑。
3. 收集 2 个「AI 说的对但其实不对」的案例（从自己的使用中），存到 `docs/ai_pitfalls.md`。

## 3.3 上下文工程：让 AI 读到你的硬件

- **时长**：20 分钟
- **画面形式**：录屏 + 目录结构图
- **本讲目标**：建立「上下文目录规范」；会把手册摘录/API 文档喂给 AI；让 AI 在正确的硬件事实上写代码。
> 本讲把你的想法——「源码放到同个路径下，告诉他怎么调用、怎么跟 AI 对话」——升级成可复用的规范。

### 前置

3.2 完成，知道「AI 会编造、要查证」。

### 知识点

**1. 从「源码放同一路径」到「上下文目录」**

你的想法：把从网上下载的源码放到同一个路径下，告诉 AI 怎么调用、怎么对话。这一步很对，本讲把它升级成四类目录：

```
project/
├── docs/          # 硬件真相：手册摘录、寄存器表、时序要求、引脚图
├── ref/           # 参考实现：官方例程、下载的驱动（只读）
├── src/           # 你的目标代码（AI 要改的地方）
├── prompts/       # 提示词模板 + 对话存档（可复用）
├── test/          # 测试用例（第 4 章展开）
└── README.md      # 工程说明书（给 AI 的第一入口）
```

**2. `docs/` 怎么写（喂给 AI 的「硬件真相」）**

- 手册摘录：把「只需要的」寄存器位定义抄出来，不要塞整本 RM（太长，AI 会被淹没）。
- 例 `docs/ledc_pwm.md`：
  ```markdown
  # LEDC PWM（ESP32，IDF v5.x）
  目标：20kHz，占空比 0-100%，GPIO18
  频率公式：f = timer_clk / (duty_res 对应计数值)
  分辨率：13 bit（占空比 0..8191）
  引脚：GPIO18，输出
  验收：示波器量 20kHz ±2%，占空比随 duty 线性变化
  ```
- 引脚表：`docs/pins.md`，列出用到的引脚与外设。
- 时序要求：电机 PWM 频率、传感器 I2C 速率、串口波特率。

**3. `ref/` 怎么用（参考实现）**

- 官方例程：`esp-idf/examples/peripherals/ledc/...` 复制到 `ref/`。
- 网上下载的驱动：放到 `ref/`，**只读**，要改就复制到 `src/` 再改。
- 关键话术：「ref 是别人的代码，src 是你的代码。AI 改 src，参考 ref。」

**4. `README.md` 与 AGENTS.md（给 AI 的说明书）**

- 内容模板：
  - 硬件：芯片型号、开发板、外设清单、引脚表
  - 工具链：ESP-IDF 版本、构建命令、烧录命令
  - 约定：编码 UTF-8、命名风格、禁止事项（如「不许改 ref/」）
  - 目录说明
- 放在工程根目录，Copilot Chat 里用 `@workspace` 或让 AI 先读 README。

**5. `prompts/` 提示词与对话存档**

- 把好用的提示词存成模板（下一讲细讲）。
- 把关键对话结论存档（AI 给的方案、你验证的结果），形成可复用的「对话资产」。

**6. 怎么让 AI「只看该看的」**

- 显式引用文件：`#file:docs/ledc_pwm.md`、`@workspace`。
- 限制范围：「只改 `src/`，不要动 `ref/`」。
- 一次任务一份上下文：不要在一个对话里混多个硬件任务。

### 演示步骤

1. **录屏（3 分钟）**：展示完整目录结构，解释每个目录的角色。
2. **录屏（5 分钟）**：现场写一份 `docs/ledc_pwm.md` 手册摘录（从官方文档抄公式与引脚）。
3. **录屏（5 分钟）**：把官方 LEDC 例程复制到 `ref/`，写 README/AGENTS.md。
4. **录屏（5 分钟）**：用 `#file:docs/ledc_pwm.md` 让 Copilot 写 PWM 驱动——对比「不喂文档」与「喂文档」两次输出的质量。
5. **录屏（2 分钟）**：演示「只改 src/」的约束指令，看 AI 是否遵守。

### 口播要点

- 「源码放同一路径是对的第一步，本讲把它升级成四类目录：硬件真相、参考实现、你的代码、提示词。」
- 「不要塞整本手册给 AI，只摘『你需要的那几页』。信息太多，AI 反而抓不住重点。」
- 「ref 只读，src 可写。AI 要改就改 src。」
- 「README 是给 AI 的说明书，也是给未来自己的说明书。」

### 踩坑提醒

- 把整本 RM 丢给 AI——效果差、token 浪费、重点被淹没。
- AI 改坏了 `ref/` 里的参考代码——diff 时才发现，加约束「只动 src/」。
- 目录里中英文混杂、命名随意——第 1 章的规范继续用。
- 不存档对话，下次重复踩坑。

### 课后动作

1. 按四类目录规范建一个新工程（可以是 LEDC PWM 或电机控制）。
2. 写 2 份 `docs/` 手册摘录（你自己要做的两个外设）。
3. 对比实验：同一提示词，「不喂 docs」与「喂 docs」各让 AI 写一次，记录质量差异。

## 3.4 提示词模板

- **时长**：18 分钟
- **画面形式**：录屏 + 模板板书
- **本讲目标**：会写「硬件约束 + 时序要求 + 验收标准 + 代码风格」的完整提示词；会用反例/正例对照改进提示词；会要求 AI 解释它写的寄存器操作。

### 前置

3.3 完成，目录规范已建。

### 知识点

**1. 提示词五要素模板**

```
【任务】一句话说清要做什么
【硬件】芯片/外设/引脚/接线（引自 docs/pins.md）
【约束】时序、频率、电平、禁止事项（引自 docs/xxx.md）
【验收】怎么算做对了（可观测：串口输出、LED、示波器量）
【风格】编码规范、命名、注释要求、只改 src/
```

- 关键话术：「提示词不是聊天，是需求规格。五要素齐了，AI 才像工程师；缺了，它就在猜。」

**2. 反例 vs 正例**

反例：
> 帮我写个 PWM

正例：
> 【任务】用 ESP-IDF LEDC 在 GPIO18 输出 PWM，驱动直流电机。
> 【硬件】ESP32 DevKitC，TB6612 驱动板，PWM 接 PWMA，方向脚 AIN1/AIN2 已由 `src/motor_dir.c` 控制，你不用管方向。
> 【约束】频率 20kHz，分辨率 13 bit，占空比 0~100%（参数 duty_percent）；改占空比时必须用预装载，避免毛刺；ESP-IDF v5.x。
> 【验收】`idf.py build` 通过；示波器量 GPIO18 得 20kHz ±2%；`motor_set_duty(30)` 时占空比约 30%。
> 【风格】C99，UTF-8，注释写「为什么」；只改 `src/pwm_motor.c` 和 `src/pwm_motor.h`，不改 `ref/`。

**3. 让 AI 解释它写的每一行寄存器操作（核对动作）**

- 追问模板：「请逐行解释你写的寄存器操作：这个地址来自哪份文档？这个位是什么含义？如果地址是编的，请明说。」
- 收到解释后：打开 `docs/` 里的手册摘录逐条对照。对不上 = 改。
- 关键话术：「让它自己说出『出处』，比你自己猜它对不对快。」

**4. 提示词的迭代技巧**

- 不满意时，先改提示词，不要先骂 AI。
- 追问模板：
  - 「哪里可能出错？列出 3 个风险点。」
  - 「换一种写法，让 ISR 更短平快。」
  - 「给出测试用例：正常、边界、异常。」
- 一次只改一个变量（硬件、约束、验收分开问），便于定位。

**5. 提示词库组织（prompts/）**

```
prompts/
```

### 演示步骤

1. **录屏（3 分钟）**：板书五要素模板。
2. **录屏（5 分钟）**：反例「帮我写个 PWM」——演示输出空泛、参数随便。
3. **录屏（6 分钟）**：正例完整提示词——输出有频率、分辨率、验收项；当场烧录验证。
4. **录屏（3 分钟）**：追问「逐行解释寄存器操作与出处」，演示对照 docs 核查。
5. **录屏（1 分钟）**：展示 `prompts/` 目录组织。

### 口播要点

- 「提示词就是需求规格。五要素：任务、硬件、约束、验收、风格。」
- 「反例『帮我写个 PWM』等于让 AI 猜你要什么。」
- 「验收标准要可观测——能用示波器量、能用串口看，不要写『正确运行』这种废话。」
- 「让它说出出处。说不出出处的地址，不许进代码。」

### 踩坑提醒

- 验收写「正常工作」——无法验证。改成「示波器量 20kHz ±2%」。
- 一次提示词塞太多任务——拆开，一次一个外设。
- 不记录提示词效果——下次重复踩坑，`prompts/` 要留使用结果。

2. 用反例/正例各跑一次，记录输出质量差异。
3. 练习追问：让 AI 解释一段它写的代码，并核查 3 个寄存器/参数的出处。

## 3.5 验证闭环 + 综合实战

- **时长**：22 分钟
- **画面形式**：录屏 + 实拍（板子/电机）
- **本讲目标**：走通「AI 生成 → 编译 → 烧录 → 观测 → 失败回喂 → 修正」的完整闭环；用 AI 完成一个驱动（循迹传感器读取或电机 PID 骨架，二选一）；学会用 Git 记录每个 AI 版本。

### 前置

3.1–3.4 完成；五要素提示词会写；目录规范已建。

### 知识点

**1. 验证闭环六步（本课方法论核心）**

```
① AI 生成代码（基于 docs/ + 提示词）
② 编译（idf.py build）——过语法/链接关
③ 烧录（idf.py flash）
④ 观测（串口 monitor / LED / 示波器 / 逻辑分析仪）
⑤ 失败信息回喂给 AI（编译报错 + 观测现象 + 已排除项）
⑥ 修正（回到①，或人工改）
```

- 关键话术：「验证闭环不是『跑一下看看』，是把观测结果当证据，回喂给 AI 让它改。」

**2. 失败回喂的正确姿势**

- 不要只贴报错。要贴：
  - 编译错误全文（含行号）
  - 观测现象（串口日志、波形、灯的状态）
  - 已排除项（我已查过时钟、已换过引脚、已换过板子）
- 模板：
  > 【现象】`idf.py build` 报 `undefined reference to ledc_set_duty`；烧录后 GPIO18 无波形。
  > 【已做】已确认 IDF v5.2；`sdkconfig` 里 LEDC 未禁用；GPIO18 无外设占用。
  > 【任务】先分析原因，再给修改；不要直接重写整个文件。

**3. 常见翻车案例集（实战中现场制造至少两个）**

| 案例 | 现象 | 回喂要点 |
|------|------|----------|
| 编造寄存器/宏 | 编译不过或行为错 | 让它改用官方 API 或给出出处 |
| 忘开外设/驱动未 install | 无输出 | 现象贴出来，让它检查 init 顺序 |
| 中断号/引脚错 | ISR 不触发 | 让它对照 `docs/pins.md` |
| 阻塞式死循环 | 看门狗复位、串口卡 | 让它找阻塞点，改状态机 |
| 占空比毛刺 | 电机顿挫 | 让它使能预装载 |

**4. 用 Git 记录每个 AI 版本**

- 每次「AI 生成 → 验证通过/失败」做一次 commit。
- commit message 写清：AI 生成了什么、验证结果如何（通过/失败/待查）。
- 好处：可回滚对比、可复盘 AI 的失败模式、第 4 章 Git 会系统化。

**5. 综合实战（二选一）**

**选项 A：循迹传感器读取（ADC）**
- 8 路灰度/红外循迹模块 → ADC 采样 → 阈值判断 → 输出「偏左/居中/偏右」。
- 用到：ADC 驱动、GPIO、串口打印、定时采样。
- 五要素提示词 + docs 摘录 + 验证闭环全程。

**选项 B：电机 PID 骨架（PWM + 编码器）**
- 目标速度设定 → 编码器测速 → PID 计算 → 改 PWM 占空比。
- 用到：LEDC PWM、编码器（脉冲计数）、定时器、串口。
- 本讲只做骨架（比例项即可），完整 PID 留第 4 章。

- 关键话术：「实战不是为了炫技，是为了让你亲手走一遍闭环——AI 写、你验、错了回喂。」

### 演示步骤

1. **录屏（3 分钟）**：画验证闭环六步图，说明每步产出什么证据。
2. **录屏（10 分钟）**：现场选一个题目（建议 A），用五要素提示词让 AI 写初版；编译、烧录、观测。
3. **录屏（4 分钟）**：故意制造一次失败（如把引脚写错），演示「失败回喂」的正确姿势，让 AI 修正。
4. **实拍（3 分钟）**：最终效果——串口打印循迹状态 / 电机按占空比转。
5. **录屏（2 分钟）**：`git log` 展示本讲的 AI 版本记录，看回滚对比。

### 口播要点

- 「闭环的关键是第⑤步：把观测当证据回喂。不要只说『没用』，要说现象、要说已排除项。」
- 「AI 第一次就写对是运气，走闭环才是常态。」
- 「每个 AI 版本一个 commit——以后回看，你会知道自己踩过哪些坑。」
- 「实战选题不重要，走完闭环才重要。」

### 踩坑提醒

- 观测没做就回喂「没用」——AI 无从下手。
- 一次改多处，不知道哪处生效——改一处验一处。
- 不 commit，验证「好像之前是对的」却回不去。
- 只看编译通过就当完成——编译通过≠硬件行为正确。

### 课后动作

1. 完成综合实战（A 或 B），保存完整 `docs/` 摘录、`prompts/` 提示词、Git 历史。
2. 写一篇《闭环实战复盘》：失败了几次、失败模式是什么、AI 帮了什么、哪一步是自己救回来的。
3. 为下一个外设（如 UART 日志、按键中断）准备五要素提示词，存 `prompts/`，供第 4 章用。
