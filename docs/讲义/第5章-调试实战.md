# 第 5 章 · 调试实战

> 对应总大纲 `docs/compose/spec/ai-embedded-teaching.md` 第 5 章。本章 4 讲，平台双平台（STM32 / ESP32 皆可）。
> 贯穿目标：学员能系统性地定位嵌入式故障，而不是「改一行试试」。调试是 AI 替代不了的 20%——本章就是那 20%。

---

## 5.1 调试思维：现象 → 假设 → 验证

- **时长**：16 分钟
- **画面形式**：动画 A11 + 板书 + 录屏
- **本讲目标**：建立「现象→假设→验证」的调试闭环思维；会用二分定位、最小复现、控制变量；知道何时加日志、何时下断点。

### 前置

第 1–4 章完成，有可调试的工程。

### 知识点

**1. 调试不是「改代码」，是「验证假设」**

- 反面：改一行 → 跑 → 不行 → 再改一行 → 跑……（随机游走）
- 正面：
  ```
  现象：电机不转
  假设1：PWM 没输出  → 验证：示波器量 GPIO
  假设2：方向脚错    → 验证：万用表量 IN1/IN2
  假设3：驱动板没使能 → 验证：量 STBY
  假设4：供电不足    → 验证：量 VM 电压
  ```
- 每个假设**必须有可观测的验证动作**。假设没法验证 = 猜想。
- 关键话术：「调试是科学家做实验，不是赌徒下注。」

**2. 三大技法**

| 技法 | 做法 | 何时用 |
|------|------|--------|
| 二分定位 | 把范围一分为二，先看哪半边坏 | 不知道从哪开始、变量多 |
| 最小复现 | 剥离到最小代码/接线，能复现 bug | bug 复杂、涉及多个模块 |
| 控制变量 | 一次只改一个变量 | 改了多处不知道哪处生效 |

- 二分例子：主循环里有 5 个模块？先注释 3 个，看 bug 在剩下 2 个还是被注释的 3 个里。
- 最小复现：单独建一个 `test_min` 工程，只留可疑模块。

**3. 日志 vs 断点：什么时候用哪个**

| 场景 | 用日志 | 用断点 |
|------|--------|--------|
| 时序相关、高频事件 | ✓（断点会扰动时序） | ✗ |
| 稳定复现的逻辑错误 | 可以 | ✓（能逐行看） |
| 跑飞 / 死机 | 难（程序已死） | 难（需观察点/回溯） |
| 想看「发生了什么」的历史 | ✓（日志留档） | ✗（断点只看当下） |

- 关键话术：「断点会『冻结世界』，时序相关的问题（中断、PWM、通信）用断点会骗你。」

**4. 日志分级与断言**

```c
#define LOG_ERR(fmt, ...)  printf("[E] " fmt "\r\n", ##__VA_ARGS__)
#define LOG_INFO(fmt, ...) printf("[I] " fmt "\r\n", ##__VA_ARGS__)
#define LOG_DBG(fmt, ...)  printf("[D] " fmt "\r\n", ##__VA_ARGS__)

assert(param != NULL);  // 失败即停，留下调用栈
```

- 级别：ERROR / WARN / INFO / DEBUG。发布版关 DEBUG。
- 断言：不变式（不该发生的事）用 assert，比事后查日志快。

**5. 调试闭环（动画 A11）**

```
现象 → 提出假设 → 设计验证 → 观测（日志/仪器）
  ↓
验证结果 → 假设成立 → 修复 → 回归测试
        → 假设不成立 → 新假设（回到上一步）
```

### 演示步骤

1. **板书（3 分钟）**：画「现象→假设→验证」闭环，标出每个假设必须可观测。
2. **动画 A11（2 分钟）**：调试思维闭环——假设树逐个被验证，绿勾/红叉，最后定位根因。
3. **录屏（5 分钟）**：现场演示「电机不转」的调试：按 4 个假设逐一验证（示波器/万用表/日志）。
4. **录屏（4 分钟）**：演示二分定位（注释模块）与最小复现（建 test_min 工程）。
5. **录屏（2 分钟）**：演示日志分级与断言。

### 口播要点

- 「改代码之前，先问：我的假设是什么？怎么验证？」
- 「不能验证的假设是猜想，猜想不配占用你的时间。」
- 「二分定位是『不知道从哪查』时的万能开场。」
- 「时序问题用日志和仪器，别用断点——断点会改变时序。」

### 踩坑提醒

- 改多处再跑——无法定位。
- 用断点查中断/PWM 时序——观测行为改变。
- 假设无法验证（「可能是干扰吧」）——改成可观测项。
- 不留日志档案——下次复现不了。

### 课后动作

1. 找一个自己项目里的 bug，写完整的「现象→假设→验证」记录（至少 3 个假设）。
2. 练习二分定位：把一个复杂 main 拆成最小复现工程。
3. 给项目加日志分级宏与一处 assert。

### 动画脚本要求（A11）

- 画面：左侧「现象」，中间假设树（每个假设一个节点），右侧「验证动作」（示波器/万用表/日志图标）。
- 动作：假设逐个点亮→验证→绿勾（保留）或红叉（排除）→最终根因节点高亮。
- 旁白：「提假设、设计验证、看结果。绿的留下，红的排除。调试是科学实验。」约 45 秒。

## 5.2 工具调试深挖

- **时长**：18 分钟
- **画面形式**：录屏（Keil / VSCode + 示意图）
- **本讲目标**：会用条件断点、数据断点（Watchpoint）、寄存器与反汇编窗口；会用 printf/ITM/RTT 日志；能定位 HardFault 并回溯调用栈。

### 前置

5.1 完成；Keil 调试基础（1.2）已会。

### 知识点

**1. 断点进阶**

| 类型 | 作用 | 何时用 |
|------|------|--------|
| 普通断点 | 停在某行 | 定位「跑没跑到」 |
| 条件断点 | 条件为真才停 | 变量在特定值时才出问题 |
| 数据断点/Watchpoint | 某地址被读/写时停 | 变量「莫名被改」 |
| 外设寄存器断点 | 外设寄存器被写时停 | 配置被覆盖 |

- 条件断点：Keil 断点属性里填条件（如 `i == 100`）。
- Watchpoint：`&变量` 被写时停——查「谁改了这个变量」神器。
- 关键话术：「变量莫名变了？下数据断点，抓『作案的手』。」

**2. 寄存器窗口与反汇编**

- 寄存器窗口：直接看外设寄存器（第 2 章用过）——验证「我写的是否生效」。
- 反汇编窗口：看 C 对应的汇编——查 volatile 是否被优化、查优化导致的奇怪行为。
- Memory 窗口：看地址内容——查内存映射、查数组越界。

**3. 日志通道三种**

| 通道 | 速度 | 侵入性 | 适用 |
|------|------|--------|------|
| printf（串口） | 慢 | 高（阻塞） | 简单、低频日志 |
| ITM（SWO） | 快 | 低 | Keil + Cortex-M3/M4（F103 可用） |
| RTT（SEGGER） | 快 | 低 | J-Link + 各平台 |

- 高频日志别用阻塞 printf——会卡主循环、改变时序。
- 关键话术：「printf 会拖慢甚至卡死你的程序。高频日志用 RTT/ITM。」

**4. HardFault / 异常定位**

- 现象：程序跑飞、灯卡死、看门狗复位。
- 定位套路：
  1. 在 HardFault_Handler 下断点。
  2. 看 `LR` / `PC`（链接寄存器 / 程序计数器）——PC 是出错指令。
  3. Keil 的 Call Stack 窗口 / 反汇编——回溯调用链。
  4. 常见原因：
     - 数组越界 / 指针野指针
     - 栈溢出（局部变量太大、递归太深）
     - 未对齐访问（Cortex-M0/M0+ 不允许）
     - 中断向量表未对齐 / 中断号错
     - 调用未初始化的函数指针

- 现场故障记录模板：
  ```
  现象：跑飞，灯停在第 3 次闪烁
  PC = 0x08001234（查反汇编 → app_motor.c:99）
  LR = 0x08001200（调用者）
  根因：hall_count[10] 越界写，踩到局部变量
  修复：改 bounds check + assert
  ```

**5. 双平台差异**

- Keil（STM32）：寄存器窗口、反汇编、Call Stack 一体，好用。
- ESP-IDF（ESP32）：VSCode + OpenOCD + JTAG 调试；也有 `esp_backtrace` 打印调用栈。
- 关键话术：「工具换了，思路不变：找 PC、回溯、定位根因。」

### 演示步骤

1. **录屏（4 分钟）**：演示条件断点（`i==100` 才停）与数据断点（谁改了 `flag`）。
2. **录屏（4 分钟）**：打开寄存器窗口、反汇编窗口、Memory 窗口各看一次。
3. **录屏（4 分钟）**：对比阻塞 printf 与 RTT/ITM 日志的时序差异（用 GPIO 翻转测执行时间）。
4. **录屏（4 分钟）**：故意制造 HardFault（数组越界），在 HardFault_Handler 下断点，看 PC/LR，回溯到出错行。
5. **录屏（2 分钟）**：ESP32 用 `esp_backtrace` 打印一次调用栈，对照 Keil 的 Call Stack。

### 口播要点

- 「变量莫名被改，下数据断点——这是抓『作案的手』最直接的办法。」
- 「printf 会拖慢甚至卡死你的程序。高频日志用 RTT/ITM。」
- 「HardFault 看 PC 和 LR。PC 是『死在哪』，LR 是『谁叫你来的』。」
- 「调用栈是你的案发现场照片。养成看 Call Stack 的习惯。」

### 踩坑提醒

- 条件断点条件写复杂表达式导致停不下来——条件要简单。
- 用 printf 打印高频中断里的日志——卡死或丢中断。
- HardFault 时不看 PC/LR 直接猜——先看现场。
- 栈溢出（局部数组太大）——见 5.4。

### 课后动作

1. 用条件断点定位一个「特定条件下才出现」的 bug。
2. 用数据断点抓一个「变量莫名被改」的案例。
3. 故意制造一次 HardFault，记录 PC/LR 与调用栈，写一份现场记录。
4. 对比一次阻塞 printf 与 RTT 日志的耗时差异（GPIO 翻转计时）。

## 5.3 硬件观测

- **时长**：20 分钟
- **画面形式**：实拍（仪器）+ 动画 A12 + 录屏
- **本讲目标**：会用万用表测供电与静态电平；会用逻辑分析仪抓 UART/I2C/SPI 时序；会用示波器看 PWM 波形与毛刺。

### 前置

5.1–5.2 完成；有万用表（必备）；逻辑分析仪/示波器（建议，没仪器可先看演示）。

### 知识点

**1. 万用表：静态三查**

| 查什么 | 怎么查 | 常见结论 |
|--------|--------|----------|
| 供电 | 直流电压档量 VCC/GND | 3.3V 是否稳、电机 VM 是否够 |
| 使能脚 | 量 STBY/片选等 | 高/低是否符合预期 |
| 电平 | 量 GPIO 静态电平 | 输出是否被拉到正确电平 |

- 关键话术：「上电第一件事不是看代码，是量电。电源不对，一切白搭。」

**2. 逻辑分析仪：数字时序（动画 A12）**

- 何时用：通信时序（UART/I2C/SPI）、PWM 频率、中断响应时间。
- 入门设备：8 通道 24MHz，几十块钱，配 PulseView / Saleae 软件。
- 操作要点：
  1. 接地（与被测板共地）——不接地波形乱。
  2. 设置采样率（UART 115200 至少 1MHz；I2C 100kHz 至少 1MHz）。
  3. 用协议解码（UART/I2C/SPI 解码器）看数据内容。
- 例：抓 UART 看是否发了 `0x55`；抓 I2C 看器件地址与 ACK。

**3. 示波器：模拟波形与毛刺**

- 何时用：PWM 波形、电源纹波、毛刺/尖刺、上升/下降沿。
- 入门要点：
  1. 探头 x1/x10 与衰减设置匹配。
  2. 触发模式（边沿触发）稳定波形。
  3. 看幅值、频率、占空比、毛刺。
- 例：PWM 期望 20kHz/50% 占空比，看是否有毛刺（4.4 的 T-003）。

**4. 仪器选择速查**

| 现象 | 首选工具 |
|------|----------|
| 电机不转、电平不对 | 万用表 |
| 串口乱码、I2C 无 ACK | 逻辑分析仪 |
| PWM 频率/占空比不对、顿挫 | 示波器（或逻辑分析仪看数字 PWM） |
| 程序跑飞 | 调试器（5.2） |
| 干扰、偶发复位 | 示波器（电源纹波）+ 排查接地 |

**5. 硬件观测与 AI 协作**

- 观测结果是给 AI 的最佳证据（3.5 的验证闭环）。
- 回喂模板：
  > 【现象】GPIO18 无波形（示波器已量）。
  > 【观测】万用表量 STBY=3.3V，VM=11.8V，逻辑分析仪量 UART 正常。
  > 【任务】据此分析可能原因。

- 关键话术：「示波器和逻辑分析仪是你的『硬件眼睛』。AI 看不见波形，只能看你贴的证据。」

### 演示步骤

1. **实拍（3 分钟）**：万用表三查演示（供电、使能脚、静态电平）。
2. **动画 A12（3 分钟）**：逻辑分析仪抓 UART/I2C 时序示意——波形逐位出现，解码器解出字节。
3. **实拍+录屏（7 分钟）**：逻辑分析仪抓一次 UART 发送（`0x55 0xAA`），解码验证；再抓 I2C 读传感器。
4. **实拍（4 分钟）**：示波器看 PWM 20kHz/50%，调 CCR 看占空比变化；演示一次毛刺（不使能预装载）。
5. **录屏（3 分钟）**：把观测结果贴给 AI，让 AI 分析原因——演示证据驱动的 AI 协作。

### 口播要点

- 「上电先量电，不量电不看代码。」
- 「逻辑分析仪看数字时序，示波器看模拟波形。分工不同。」
- 「接地！逻辑分析仪不接地，波形是乱的。」
- 「观测结果是给 AI 的证据。AI 看不见波形，只能看你贴的东西。」

### 踩坑提醒

- 逻辑分析仪没共地——波形乱跳。
- 采样率太低——通信采不到位。
- 示波器探头衰减档位错——幅值读数错。
- 只用眼睛看 LED 判断 PWM——不准确，要仪器。

### 课后动作

1. 用万用表做一次「上电三查」，记录三个电压值。
2. 用逻辑分析仪抓一次 UART 发送，解码出字节。
3. 用示波器量一次 PWM 的频率与占空比，与计算值对比。
4. 把一次仪器观测结果喂给 AI，让它分析原因。

### 动画脚本要求（A12）

- 画面：上方 UART/I2C 波形，下方解码结果（字节/地址/ACK）。
- 动作：波形逐位出现，解码器同步显示 `0x55`、`0xAA`；I2C 显示 `START`、地址、`ACK`、`DATA`、`STOP`。
- 旁白：「逻辑分析仪把波形翻译成字节。你能亲眼看到『到底发了什么』。」约 50 秒。

## 5.4 经典踩坑复盘（智能车 / 电赛向）

- **时长**：18 分钟
- **画面形式**：实拍 + 录屏 + 案例板书
- **本讲目标**：能快速排查智能车/电赛四类典型故障（电机不转、传感器抖动、跑飞死机、电源复位）；建立自己的踩坑库。

### 前置

5.1–5.3 完成；最好有智能车硬件。

### 知识点

**1. 电机不转 / 转速不对**

| 可能原因 | 验证方法 | 修复 |
|----------|----------|------|
| PWM 没输出 | 示波器量 PWM 引脚 | 查引脚复用、TIM/LEDC 使能 |
| 方向脚错 | 万用表量 IN1/IN2 | 改方向 GPIO |
| 驱动板没使能 | 量 STBY | 拉高 STBY |
| 供电不足 | 量 VM（电机电压） | 换电池/查线 |
| 不共地 | 万用表量 GND 连通 | 共地 |
| 占空比太小 | 串口打印 duty | 调 CCR/参数 |

- 关键话术：「电机不转的排查顺序：PWM→方向→使能→供电→地。五步走完，九成能定位。」

**2. 传感器抖动 / 误触发**

| 可能原因 | 验证方法 | 修复 |
|----------|----------|------|
| 按键抖动 | 逻辑分析仪看波形 | 软件消抖 / 状态机 |
| ADC 噪声 | 示波器量输入 | 滤波（均值/EMA） |
| 上拉缺失 | 量引脚空闲电平 | 加上拉电阻 |
| 干扰（电机 PWM） | 示波器看叠加毛刺 | 屏蔽/分开走线/RC 滤波 |
| 阈值不合理 | 打印采样分布 | 重新标定阈值 |

- 关键话术：「抖动是嵌入式最常见的心脏病。消抖和滤波是必修课。」

**3. 程序跑飞 / 死机**

| 可能原因 | 验证方法 | 修复 |
|----------|----------|------|
| HardFault | 断点看 PC/LR（5.2） | 修越界/指针 |
| 栈溢出 | 查栈用量、局部大数组 | 加大栈/改动态分配（谨慎） |
| 中断风暴 | 看 ISR 是否清标志 | 清中断标志 |
| 看门狗复位 | 看复位原因寄存器 | 喂狗 / 查长阻塞 |
| 优先级问题 | 查 NVIC 配置 | 调优先级 |
| 未初始化变量 | 代码 review + 静态检查 | 初始化 |

- 关键话术：「跑飞先看复位原因与 PC。栈溢出和越界是两大常见凶手。」

**4. 电池电压跌落导致复位**

- 现象：电机一启动就复位、跑一会就死。
- 原因：电机堵转/启动电流大 → 电压跌落 → MCU 复位。
- 验证：示波器量 VCC 在电机启动瞬间的跌落。
- 修复：
  - 电源分离（电机电源与逻辑电源分开 + 共地）
  - 加大电容（100uF~1000uF）
  - 软启动（占空比斜坡上升，不要瞬间 100%）
  - 用带稳压的电池盒

- 关键话术：「电赛赛场上，电源问题占一半的『跑飞』。电机一动就死机，先量电压。」

模板：
```markdown
## PIT-001 电机一启动就复位
- 现象：上电正常，按下前进键瞬间复位
- 根因：电机启动电流导致 5V 跌至 3.8V
- 验证：示波器量 VCC 启动瞬间
- 修复：软启动 + 1000uF 电容
- 关联讲次：5.4、2.7
```

- 关键话术：「踩坑库是你的私人军火库。同一个坑，绝不踩第二次。」

### 演示步骤

1. **实拍（5 分钟）**：制造「电机不转」（拔 STBY），按五步排查走一遍。
2. **实拍（4 分钟）**：制造「按键抖动」（无消抖），逻辑分析仪看抖动；加消抖后修复。
3. **录屏（4 分钟）**：制造 HardFault（数组越界），按 5.2 方法定位。
4. **实拍（3 分钟）**：演示「电机一启动就复位」（小电容/分离电源），示波器量电压跌落，加电容后修复。
5. **录屏（2 分钟）**：写一份 `pitfalls.md`，填 PIT-001 到 PIT-004。
