# 第 4 章 · 工程框架与迭代

> 对应总大纲 `docs/compose/spec/ai-embedded-teaching.md` 第 4 章。本章 5 讲，平台 ESP32。
> 贯穿目标：把「能跑的代码」变成「可迭代的工程」——分层、Git、文档驱动、测试闭环、系统性迭代节奏；最后收束智能车核心功能。
> 本章回答你的核心诉求：「怎么系统性地迭代工程、用 git、文本文档循环测试、闭环测试」。

## 4.1 从「能跑」到「工程」

- **时长**：18 分钟
- **画面形式**：录屏 + 目录结构图
- **本讲目标**：能诊断「单文件 main.c」的问题；能按 driver/app/util 三层拆分代码；能组织头文件与编译单元，避免重复包含。

### 前置

第 3 章完成，至少有一个能跑的外设驱动。

### 知识点

**1. 单文件 main.c 的问题**

| 问题 | 后果 |
|------|------|
| 硬件操作和业务逻辑混在一起 | 换平台/换外设要重写全部 |
| 几千行找一个函数 | 阅读/调试成本高 |
| 复制粘贴改参数 | bug 隐藏在重复代码里 |
| 没法单元测试 | 硬件依赖和逻辑耦合 |
| AI 改一处动全身 | 容易改坏不相干的代码 |

- 关键话术：「能跑 ≠ 工程。工程是让你三个月后还能改得动、别人也能接手。」

**2. 三层分层（本课的工程骨架）**

```
src/
├── driver/     # 硬件层：只摸寄存器/官方 API，不含业务
│   ├── pwm_motor.c/.h
│   ├── adc_track.c/.h
│   └── uart_log.c/.h
├── app/        # 业务层：策略、状态机、控制逻辑
│   ├── app_motor.c/.h
│   └── app_track.c/.h
└── util/       # 工具层：纯逻辑，无硬件依赖（可 PC 单测）
    ├── pid.c/.h
    └── filter.c/.h
```

| 层 | 依赖 | 能否 PC 单测 | 换平台代价 |
|----|------|--------------|------------|
| driver | 寄存器/官方 API | 否（需 mock） | 高（重写 driver） |
| app | driver 接口 | 部分 | 低 |
| util | 无硬件 | 是 | 零 |

- 分层规则：
  - `app/` 不直接摸寄存器，只调 `driver/` 的接口。
  - `util/` 不 include 任何硬件头文件。
  - `driver/` 不写业务决策（如「速度超过 X 就刹车」）。
- 关键话术：「业务永远不摸寄存器。换平台时，你只想重写 driver 层。」

**3. 头文件与编译单元**

- 每个 `.c` 对应一个 `.h`，`.h` 只放：宏、类型、函数原型。
- **Include guard**（防重复包含）：
  ```c
  #ifndef DRV_PWM_MOTOR_H
  #define DRV_PWM_MOTOR_H
  // ...
  #endif
  ```
  或 `#pragma once`。
- **依赖方向单向**：`app → driver → (寄存器/API)`；不要反过来 include。
- 前向声明（`struct Foo;`）减少头文件互相包含。

**4. 配置与常量集中**

- `config.h` / `sdkconfig`：引脚号、频率、阈值等集中一处，不要散在代码里用魔数。
- 关键话术：「魔数是三个月后看不懂的自己。把 20000 提成 `PWM_FREQ_HZ`。」

**5. 与 AI 协作的工程约束**

- AGENTS.md 里写清分层规则与「不许改 ref/」。
- 提示词里加：「只改 `src/app/app_motor.c`，不要动 `src/driver/`」。
- 让 AI review 时问：「是否违反分层依赖方向？」

### 演示步骤

1. **录屏（3 分钟）**：展示第 3 章的「一坨 main.c」，指出找函数、改参数、换平台的痛点。
2. **录屏（6 分钟）**：现场重构——把 PWM、串口、业务逻辑拆到 `driver/app/util`；编译烧录验证行为不变。
3. **录屏（4 分钟）**：写一个 `config.h`，把魔数提成宏；加 include guard。
4. **录屏（3 分钟）**：演示错误依赖（app 直接 include 寄存器头）并修正。
5. **录屏（2 分钟）**：更新 AGENTS.md，写入分层规则；让 Copilot review 是否遵守。

### 口播要点

- 「能跑是 60 分，工程化才是 90 分。」
- 「业务不摸寄存器——这是分层的第一铁律。」
- 「util 层不碰硬件，将来能在电脑上直接跑单元测试。」
- 「魔数提成宏，是给未来的自己和 AI 省时间。」

### 踩坑提醒

- 过度分层（一层一个文件夹、五个抽象层）——初学三层够了。
- 头文件互相 include 成环——用前向声明。
- 重构后不验证行为——每次拆分后立刻编译烧录对比。
- AI 改代码时改到 `ref/`——加约束 + diff review。

### 课后动作

1. 把第 3 章的实战代码重构为 `driver/app/util` 三层，行为保持一致。
2. 写一份 `config.h`，列出本项目所有引脚与常量。
3. 让 Copilot review 一次分层依赖，记录它发现的问题。

## 4.2 Git 工作流

- **时长**：20 分钟
- **画面形式**：录屏 + 分支图
- **本讲目标**：能初始化仓库、写规范 commit、用分支做功能开发；会用 `git blame` / `git diff` / `git bisect` 调试；会让 AI 生成规范 commit message。

### 前置

4.1 完成，代码已分层；已装 Git。

### 知识点

**1. 初始化与 .gitignore**

```
git init
git add .
git commit -m "chore: 初始工程骨架（三层分层）"
```

- `.gitignore` 必备：
  ```
  build/
  sdkconfig.old
  .vscode/
  *.o
  *.exe
  .DS_Store
  ```
- 不要提交：编译产物、IDE 临时文件、密钥（`sdkconfig` 里若含 WiFi 密码要注意）。

**2. Commit 规范：说清「为什么」**

- 坏：`fix bug`、`update`、`改了一下`
- 好：
  ```
  fix(pwm): 使能预装载，消除占空比毛刺

  现象：duty 从 30% 调到 70% 时电机顿挫。
  原因：CCR 直接写，未用预装载寄存器。
  验证：示波器量 GPIO18，毛刺消失。
  ```
- 常用前缀：`feat:` `fix:` `docs:` `refactor:` `test:` `chore:`
- 关键话术：「commit message 是写给三个月后的自己看的。写『为什么』，不是『改了什么』。」

**3. 分支模型（轻量版）**

```
main ──────── 稳定可发布
  └─ develop ─ 日常集成
       ├─ feature/pwm-motor
       ├─ feature/track-adc
       └─ fix/hardfault
```

- `main`：可发布状态。
- `feature/*`：一个功能/外设一条分支，做完合回 develop。
- `fix/*`：修 bug。
- 关键话术：「一人开发也用分支——main 永远是『能跑的版本』，脏活在分支上干。」

**4. 调试三板斧**

| 命令 | 用途 | 何时用 |
|------|------|--------|
| `git diff` | 看改了什么 | 改完 review、AI 改完检查 |
| `git blame` | 这行是谁/哪次改的 | 排查「什么时候坏的」 |
| `git bisect` | 二分定位引入 bug 的 commit | 「之前还是好的」 |

- `git bisect` 流程：
  ```
  git bisect start
  git bisect bad            # 当前是坏的
  git bisect good <commit>  # 某个好的提交
  # Git 自动 checkout 中间版本，你编译烧录测试
  git bisect good / git bisect bad
  # 重复直到定位到第一个坏 commit
  git bisect reset
  ```

**5. AI 时代的 commit**

- 让 AI 生成 commit message 的提示词：
  > 【任务】根据 `git diff` 生成 commit message。
  > 【风格】`type(scope): 摘要` + 正文写「为什么」与「验证方式」。
  > 【禁止】不要写「AI 生成」；不要编造未做的验证。
- 人工 review：AI 可能把「改了什么」写得很漂亮，但「为什么」是编的——你要核对。
- 关键话术：「AI 写 commit 很快，但『为什么』必须是真的。」

**6. AI 版本记录（承接 3.5）**

- 每次「AI 生成 → 验证」一个 commit，便于回滚对比 AI 的失败模式。
- 用 `git log --oneline` 看迭代轨迹，写迭代日志。

### 演示步骤

1. **录屏（3 分钟）**：`git init`、写 `.gitignore`、首个 commit。
2. **录屏（4 分钟）**：演示坏 commit vs 好 commit 的 message。
3. **录屏（4 分钟）**：建 `feature/pwm-motor` 分支，做一次功能提交，合回 develop。
4. **录屏（5 分钟）**：`git blame` 找一行代码的来历；`git diff` review 一次 AI 的改动。
5. **录屏（3 分钟）**：`git bisect` 演示（可以制造一个故意的 bug 提交链）。
6. **录屏（1 分钟）**：让 AI 生成 commit message，人工核对「为什么」是否属实。

### 口播要点

- 「main 永远是能跑的版本。脏活在 feature 分支干。」
- 「commit 写『为什么』——现象、原因、验证。三行字，救你三个月。」
- 「git bisect 是『之前还是好的』的标准答案。」
- 「AI 写 commit 又快又好，但『为什么』和『验证方式』必须你核对。」

### 踩坑提醒

- 提交了 `build/` 或 `sdkconfig`（含密码）——`.gitignore` 要写对。
- 一次性 commit 改了 50 个文件——拆小，一次一个逻辑变更。
- 不写验证方式——三个月后不知道当时怎么测的。
- bisect 时没编译烧录就标 good/bad——结论是错的。

### 课后动作

1. 把 4.1 的工程 `git init`，写好 `.gitignore`，提交初始版本。
2. 用 `feature/*` 分支做一次功能开发并合并。
3. 练习 `git bisect`：人为制造 5 个 commit，其中第 3 个引入 bug，定位它。
4. 让 AI 生成 3 条 commit message，核对「为什么」是否属实。

## 4.3 文档驱动开发

- **时长**：18 分钟
- **画面形式**：录屏 + 三方对照表
- **本讲目标**：会写需求文档与测试用例文档；掌握「需求-测试-代码三方对照」；养成「先改文档再改代码」的循环习惯。
> 本讲落地你的想法——「文本文档循环测试」：文档不是写完就扔，而是每次迭代的循环入口。

### 前置

4.1–4.2 完成，工程已有 Git 管理。

### 知识点

**1. 为什么文档驱动**

- 没文档的迭代：改哪算哪，需求说不清，AI 只能猜。
- 文档驱动：需求写清 → 测试用例定义「怎么做算对」→ 代码实现 → 对照验证。
- 关键话术：「文档不是给人看的，是给『改代码这件事』定规矩的。」

**2. 三份核心文档**

| 文档 | 回答 | 位置 |
|------|------|------|
| 需求文档 | 要做什么、约束是什么 | `docs/requirements.md` |
| 设计文档 | 怎么做、模块怎么划分 | `docs/design.md` |
| 测试用例 | 怎么算做对了 | `test/testcases.md` |

**3. 需求-测试-代码三方对照表（本讲核心工具）**

| 需求 ID | 需求描述 | 测试用例 ID | 验收标准 | 代码位置 | 状态 |
|---------|----------|-------------|----------|----------|------|
| R-001 | PWM 20kHz 驱动电机 | T-001 | 示波器量 20kHz ±2% | `driver/pwm_motor.c` | 已验证 |
| R-002 | 占空比 0~100% 线性 | T-002 | duty=30% 时约 30% | 同上 | 已验证 |
| R-003 | 改占空比无毛刺 | T-003 | 示波器无尖刺 | 同上 | 失败（待修） |

- 表格怎么用：
  - **写代码前**：先把 R 与 T 填好（只填需求与验收）。
  - **写代码时**：填「代码位置」。
  - **验证后**：填「状态」（已验证 / 失败 / 待查）。
  - **下次迭代**：先改 R/T，再改代码。
- 关键话术：「这张表是项目的地图。AI 不知道需求时，把这张表喂给它。」

**4. 文档循环测试（你的提法落地）**

「文本文档循环测试」= 以文档为循环入口的测试流程：

```
改需求文档 R
    ↓
改/补测试用例 T（写清验收）
    ↓
改代码 C
    ↓
执行测试（板级观测 / 单元测试）
    ↓
回填三方对照表状态
    ↓
（失败则回喂 AI 或人工修，回到上一步）
```

- 关键：**每次迭代从改文档开始**，不是从改代码开始。
- 文档是 AI 的上下文源（3.3 的 `docs/`）——改完文档，AI 的上下文自动跟着变。

**5. 测试用例怎么写（可执行的文本）**

```markdown
## T-001 PWM 频率
- 前置：烧录 `firmware.elf`，GPIO18 接示波器
- 步骤：调用 `motor_set_duty(50)`
- 期望：示波器量得 20000Hz ±2%，占空比 50% ±2%
- 失败处理：记录波形截图，回喂 AI，禁用「猜」
```

- 要素：前置、步骤、期望（可观测）、失败处理。
- 关键话术：「期望不能是『正常』，必须是示波器能量、串口能看到的东西。」

**6. 文档是给 AI 的上下文**

- 把 `docs/requirements.md`、`test/testcases.md` 放进上下文目录。
- 提示词里写：「实现 R-001 到 R-003，验收见 T-001 到 T-003，不要实现未列出的需求。」

### 演示步骤

1. **录屏（3 分钟）**：展示无文档迭代的混乱（需求说不清、AI 猜）。
2. **录屏（5 分钟）**：写一份 `requirements.md`（3 条需求）与 `testcases.md`（对应 3 条用例）。
3. **录屏（4 分钟）**：建三方对照表，填 R/T，代码位置留空。
4. **录屏（4 分钟）**：让 AI 按 R-001..003 写代码（提示词里喂文档）；跑测试，回填状态。
5. **录屏（2 分钟）**：演示「下次迭代先改文档」——改 R-002 的占空比范围，看对照表与代码怎么跟着变。

### 口播要点

- 「先改文档，再改代码。文档是循环的入口。」
- 「三方对照表：需求、测试、代码。三样对得上，才算做完。」
- 「测试期望必须可观测——示波器能量、串口能看到。」
- 「把文档喂给 AI，它才知道你要什么，不需要未列出的需求。」

### 踩坑提醒

- 文档写完就过期——每次迭代同步更新三方对照表。
- 测试用例写「正常工作」——改可观测指标。
- 只写需求不写测试——没有验收，无法判定完成。
- AI 实现了文档没写的需求（自己发挥）——提示词里明确「不要实现未列出的需求」。

### 课后动作

1. 为你的项目写 `requirements.md`（≥3 条）与 `testcases.md`（对应 ≥3 条）。
2. 建三方对照表，先填 R 与 T。
3. 用文档驱动做一次迭代：改文档 → 改代码 → 验证 → 回填状态。
4. 把三方对照表喂给 AI，看它是否只实现列出的需求。

## 4.4 测试闭环

- **时长**：20 分钟
- **画面形式**：动画 A10 + 录屏
- **本讲目标**：掌握三层测试（单元测试 / 板级自测 / 回归金标准）；会写可执行的文本测试用例；能跑通完整测试闭环。
> 本讲把「文本文档循环测试」扩展成完整的测试闭环。

### 前置

4.3 完成，三方对照表已建。

### 知识点

**1. 三层测试**

| 层 | 跑在哪 | 测什么 | 工具 |
|----|--------|--------|------|
| 单元测试 | PC | `util/` 纯逻辑（PID、滤波、状态机） | Unity / 自写 assert |
| 板级自测 | 板上 | 外设行为（PWM 频率、ADC 精度、中断响应） | 串口指令 + 脚本 |
| 回归/金标准 | 板上 | 整体行为是否与基准一致 | 日志 diff / 波形对比 |

- 关键话术：「单元测试在电脑上跑，快；板级自测在板上跑，真；金标准防『改了东墙塌了西墙』。」

**2. 单元测试（PC 上跑 util 层）**

- 为什么 util 层不碰硬件（4.1 的规则）——就是为了能在 PC 上测。
- 最小测试框架（自写 assert 即可）：
  ```c
  // test/test_pid.c
  #include <assert.h>
  #include "util/pid.h"
  void test_pid_step(void) {
      PID_t pid; pid_init(&pid, 1.0f, 0.1f, 0.0f);
      float u = pid_step(&pid, 10.0f, 0.0f); // 目标10 当前0
      assert(u > 0); // 输出应为正
  }
  ```
- ESP-IDF 自带 Unity 测试框架（`idf.py test`），也可以先用简单 assert 起步。
- 关键话术：「PID 算错不该等到上车才发现。在电脑上测。」

**3. 板级自测（串口指令 + 脚本）**

- 让固件暴露测试指令（串口命令）：
  ```
  T PWM_FREQ     → 打印实测频率（或用输入捕获测）
  T ADC_CH0      → 打印采样值
  T ISR_LATENCY  → 打印中断响应计数
  ```
- 用脚本（Python）发指令、收输出、对比期望：
  ```python
  # test/run_board_test.py（示意）
  # 发送 "T PWM_FREQ\n"，期望回复 "20000 Hz"
  ```
- 关键话术：「测试指令是给回归测试用的『钩子』。没有钩子，每次都要手点。」

**4. 回归测试与金标准**

- **金标准（golden）**：一份「已知正确」的日志/波形/行为快照。
- 测试流程：跑新固件 → 收集日志 → 与金标准 diff → 差异要么是预期改进（更新金标准），要么是 bug。
- 例子：
  - 金标准日志：`golden_run_20260922.log`（电机 0→30%→70% 三段日志）
  - 新版本日志：`run_20260928.log`
  - diff 工具对比，差异标注。
- 关键话术：「改一处塌一片，只有金标准对比能发现。」

**5. 测试闭环流程（动画 A10）**

```
需求文档 R → 测试用例 T → 代码 C
    ↓             ↓
（单元测试）  （板级自测）
    ↓             ↓
        结果对比（回归/金标准）
    ↓
  通过 → 更新三方对照表 / 更新金标准
  失败 → 回喂 AI 或人工修，回到 C
```

**6. 闭环与 AI 协作**

- 测试失败信息是给 AI 的最佳上下文（3.5 的验证闭环）。
- 让 AI 写测试用例的提示词：
  > 【任务】为 `util/pid.c` 写单元测试。
  > 【关注】P/I/D 各项、输出限幅、积分饱和（若实现）、边界（目标=当前、误差极大）。
  > 【输出】`test/test_pid.c`，用 assert，可 PC 编译运行。

### 演示步骤

1. **动画 A10（3 分钟）**：测试闭环流程图——需求/测试/代码三线并行，汇聚到测试执行，再反馈回代码。
2. **录屏（5 分钟）**：给 `util/pid.c` 写 PC 单元测试，编译运行，看到 pass/fail。
3. **录屏（5 分钟）**：固件加串口测试指令 `T PWM_FREQ`；Python 脚本发指令、解析、对比期望。
4. **录屏（4 分钟）**：录一份「金标准日志」，改一处参数跑新版本，diff 对比。
5. **录屏（3 分钟）**：故意让一个测试失败，演示「失败回喂 AI」的闭环。

### 口播要点

- 「单元测试在电脑上，板级自测在板上，金标准防回归。三层各有分工。」
- 「测试指令是回归的钩子。没有钩子，每次都要手点，就无法自动化。」
- 「金标准是『已知正确』的快照。改了代码，拿新日志和它比。」
- 「测试失败是最好的 AI 上下文——现象、期望、已排除项，一起回喂。」

### 踩坑提醒

- 只做板级测试不做单元测试——PID 等逻辑改动风险大。
- 测试用例不可执行（「性能良好」）——改可观测指标。
- 金标准不更新——预期改进被当 bug。
- 测试通过就完事——测试也要随需求更新（4.3 的循环）。

### 课后动作

1. 给 `util/` 里一个纯逻辑模块写 PC 单元测试（≥3 个 case）。
2. 给固件加 2 条串口测试指令，并写脚本自动跑。
3. 录一份金标准日志，做一次 diff 对比。
4. 演示一次「测试失败 → 回喂 AI → 修正 → 通过」的完整闭环。

### 动画脚本要求（A10）

- 画面：三栏（需求 / 测试 / 代码）→ 中间「执行测试」圆 → 分叉「通过 / 失败」→ 失败回箭头到代码，通过回箭头到对照表。
- 动作：数据流从三栏汇入执行测试，绿勾走上路，红叉走回路。
- 旁白：「需求定义要什么，测试定义怎么算对，代码去实现。失败就回去改，通过才更新地图。」约 50 秒。

## 4.5 迭代节奏 + 主线项目收束（智能车核心功能）

- **时长**：22 分钟
- **画面形式**：录屏 + 实拍（智能车）
- **本讲目标**：掌握小步提交、可回滚的系统性迭代节奏；会做版本号与变更日志；用 1–4 章方法在 ESP32 上实现智能车核心（循迹 + 避障 + 电机调速），并做迭代复盘。

### 前置

4.1–4.4 完成；智能车硬件（电机、驱动板、循迹模块、超声波）已就位。

### 知识点

**1. 系统性迭代 vs 东一榔头西一棒**

| 反面（东一榔头） | 正面（系统性迭代） |
|------------------|---------------------|
| 想到哪改到哪 | 先改文档（4.3）定范围 |
| 一次 commit 改 30 处 | 一次 commit 一个逻辑变更 |
| 改完不测 | 每步跑测试（4.4） |
| 改坏了不知哪坏 | 小步提交可回滚（4.2） |
| 月底才发现跑偏 | 每次迭代更新三方对照表 |

- 迭代节奏（建议）：
  ```
  ① 改文档（R/T）      ← 定「这次改什么」
  ② 开 feature 分支
  ③ 小步提交（每步编译通过）
  ④ 跑测试闭环
  ⑤ 合回 develop
  ⑥ 更新三方对照表 + 版本号
  ```
- 关键话术：「一次迭代做一件事。做完测完再做下一件。」

**2. 小步提交与可回滚**

- 一次提交 = 一个逻辑变更（一个 R 的实现 / 一个 bug 修复）。
- 提交前：编译通过 + 测试通过（至少不比之前差）。
- 回滚：`git revert` 或 `git reset`（未 push 时）。

**3. 版本号与变更日志**

- 语义化版本：`主版本.次版本.修订`（如 `1.2.3`）。
  - 主：不兼容变更
  - 次：新功能
  - 修订：bug 修复
- `CHANGELOG.md`：
  ```markdown
  ## [1.1.0] - 2026-09-28
  ### Added
  - R-005 超声波避障
  ### Fixed
  - T-003 占空比毛刺（使能预装载）
  ```
- 发布打 tag：`git tag v1.1.0`。

**4. CI 雏形（无硬件也能跑）**

- 即使没板子，也能自动跑：
  - 编译（`idf.py build`）
  - 单元测试（PC）
  - 静态检查（`clang-tidy` / `cppcheck`，可选）
- GitHub Actions / Gitea Actions / 本地脚本均可。
- 关键话术：「CI 是『每次提交都编译一遍』，把低级错误挡在门外。」

**5. 主线项目收束：智能车核心**

功能范围（本讲实现）：
1. **电机调速**：LEDC PWM + 方向 GPIO（2.7 + 3.5 的能力）
2. **循迹**：ADC 读灰度/红外 → 阈值/加权 → 输出偏移量（3.5 选项 A）
3. **避障**：超声波测距 → 距离 < 阈值 → 停车/转向
4. **串口日志**：打印状态，供测试闭环用

工程化落地（本章全程）：
- `driver/`：pwm_motor、adc_track、ultrasonic、uart_log
- `app/`：app_control（循迹+避障状态机）
- `util/`：pid（简单 P 控制即可）
- 文档：requirements、design、testcases、三方对照表
- Git：feature 分支、规范 commit、版本 tag
- 测试：PC 单测 + 板级串口测试 + 金标准日志

**6. 迭代复盘（本讲结尾必做）**

- 哪些环节省了时间？（提示词库、上下文目录、测试钩子）
- 哪些 AI 帮倒忙？（编造地址、过度设计、改坏无关代码）
- 三方对照表是否完整？状态是否都已回填？
- 金标准是否更新到最新？

- 关键话术：「项目做完不是终点，复盘才是。把坑记下来，下个项目少踩一次。」

### 演示步骤

1. **录屏（3 分钟）**：对比「东一榔头」与「系统性迭代」两张表。
2. **录屏（8 分钟）**：现场实现智能车核心的一个功能（如避障），走完整流程：改文档→分支→小步提交→测试→合并。
3. **实拍（6 分钟）**：智能车整体演示——循迹、避障、调速；串口日志同步显示。
4. **录屏（3 分钟）**：`git log --oneline` + `CHANGELOG.md` + `git tag`，展示迭代轨迹。
5. **录屏（2 分钟）**：现场做迭代复盘，填复盘表。

### 口播要点

- 「一次迭代做一件事。做完测完再做下一件。这是系统性和东一榔头的分水岭。」
- 「小步提交 + 测试通过 + 版本 tag = 可回滚、可追溯。」
- 「CHANGELOG 写给用户和未来的自己，tag 写给发布。」
- 「CI 把『忘了编译』这类低级错误挡在门外。」
- 「复盘不是形式，是把『这次踩的坑』变成『下次的免疫』。」

### 踩坑提醒

- 一次迭代塞多个需求——拆开，一次一个 R。
- 不跑测试就合并——回归风险。
- 版本号乱标——用语义化版本。
- 复盘只说好话——必须记「AI 帮倒忙」的案例。

### 课后动作

1. 完成智能车核心功能（循迹 + 避障 + 调速），走完整迭代流程。
2. 写一份 `CHANGELOG.md`，打一个 `v1.0.0` tag。
3. 做一次完整复盘，输出《迭代复盘报告》：省时间的环节、AI 帮倒忙的案例、改进清单。
4. （可选）搭一个最简 CI：提交时自动 `idf.py build`。
